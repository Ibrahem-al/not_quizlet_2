How to read this report. Each framework section contains numbered tests. Every test lists Source, Control ID, Category, Control Description, Procedure (what I did), Evidence (what I observed), Findings, Recommendations, and Risk Level — the same fields as the assessor worksheet template, but rendered as a compact ordered list instead of a repeated table. Tests are divided by a horizontal separator. Risk levels: Pass Partial Fail N/A.
Important caveats. (1) This is a source-code and configuration review. No dynamic penetration testing, credential spraying, or live exploit attempts were performed against the production deployment. (2) Supabase-managed infrastructure (TLS, DB encryption-at-rest, auth token signing) was not audited inside Supabase's console — findings about those rely on Supabase's documented defaults. (3) STIG ASD V4R9 targets DoD systems; many controls are applied here as industry best-practice analogs, since StudyFlow is a consumer study app (not a DoD ATO candidate). Controls that clearly don't apply (e.g., SOAP signing, data marking for classified data, CAC auth) are omitted rather than marked N/A. (4) No third security framework was supplied in security/; OWASP Top 10 (2021) was selected as the third because it is the de-facto web-application baseline and complements STIG (DoD-flavored) and CIS (enterprise-flavored).

Category
Session Management
Control Description
The application must provide a capability to limit the number of logon sessions per user, to reduce DoS risk and session-hijacking exposure.
Procedure (what I did)

S-02Clear temporary storage and cookies on session termination

Fail
Source
DISA STIG ASD V4R9
Control ID
APSC-DV-000060 (SRG-APP-000295, CAT II, CCI-002361)
Category
Session Management / Client Storage
Control Description
The application must clear temporary storage (cookies, localStorage, IndexedDB) when the session is terminated.
Procedure
  1. Read the logout handler: signOut in src/stores/useAuthStore.ts.
  2. Grep for localStorage/IndexedDB references cleared at logoff.
  3. Inspect src/lib/cloudSync.ts for localStorage keys (e.g., sf_pending_set_deletes) and the Dexie instance.
Evidence
// src/stores/useAuthStore.ts
signOut: async () => {
  if (supabase) { await supabase.auth.signOut(); }
  set({ user: null, session: null });
},

The signOut path only invalidates the Supabase session; it does not clear: the Dexie studyflow IndexedDB (contains the user's full sets, cards, study history), localStorage keys (sf_pending_set_deletes, sf_pending_folder_deletes, studyflow-theme), or the Supabase-SDK sb-<project>-auth-token entries (SDK does clear its own token, but app data remains).

Findings

On a shared device, after sign-out a subsequent visitor can browse the previous user's entire library via IndexedDB inspection (DevTools → Application → IndexedDB → studyflow). This violates the "clear temporary storage" intent, even though it is an intentional offline-first design choice.

Recommendations
  • On explicit sign-out, offer the user a prompt: "Clear downloaded sets from this device?" and, if accepted, call indexedDB.deleteDatabase('studyflow') and wipe the sf_* localStorage keys.
  • For a shared-device mode, always clear on sign-out.
  • Document the retention decision in APP_SPECIFICATION.md so the tradeoff is explicit.

Fail

DISA STIG ASD V4R9
Control ID
APSC-DV-000070 (SRG-APP-000295, CAT II, CCI-002361)
Category
Session Management / Idle Timeout
Control Description
The application must automatically terminate the non-privileged user session after 15 minutes of inactivity.
Procedure
  1. Grep: Grep "idle|timeout|inactivity|SESSION_TIMEOUT".
  2. Search src/ for visibilitychange / activity listeners.
  3. Inspect Supabase client options in src/lib/supabase.ts for explicit session-refresh config.
Evidence

All matches for idle|timeout|inactivity were unrelated (card-flip game timeouts, network error strings). src/lib/supabase.ts creates the client with default options — Supabase JWTs default to 1 hour with auto-refresh for 365 days of refresh-token validity.

No idle-timeout policy exists in the app. A logged-in session persists indefinitely on the client as long as the refresh token is valid.

  • If the offline-first requirement conflicts with idle lockout, scope the control to "cloud features disabled after 15 min idle" while offline study remains available.

C-04C5.2 — Use unique passwords (length + reuse)

Partial
Source
CIS Controls v8
Control ID
CIS 5.2 (Control 5: Account Management, IG1)
Category
Identity & Authentication
Control Description
Use unique passwords for all enterprise assets — min 8 char for MFA accounts, 14 char for password-only. Enforce non-reuse.
Procedure
  1. Read password validation in SignUpPage.tsx, AccountSettingsPage.tsx, ResetPasswordPage.tsx.
  2. Read the check_password_reuse Postgres function in 001_initial_schema.sql.
Evidence
// All password entry forms enforce 12-char minimum
if (password.length < 12) {
  setError('Password must be at least 12 characters.');
  return;
}
-- supabase/migrations/001_initial_schema.sql — check_password_reuse is stubbed:
RETURNS BOOLEAN LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE reused BOOLEAN := false;
BEGIN
  SELECT EXISTS(
    SELECT 1 FROM password_history
    WHERE user_id = p_user_id
    ORDER BY created_at DESC LIMIT 5
  ) INTO reused;
  -- NOTE: Real implementation needs bcrypt comparison via pgcrypto
  RETURN reused;
END;
$$;
Findings

The 12-character minimum meets CIS's 14-char standard only partially (12 is close, 14 is the spec). More importantly, the check_password_reuse function is a no-op: it returns true whenever any history row exists for the user, regardless of the submitted password. This means every password change after the first one is falsely reported as "reused," or — depending on how the client interprets the missing .reused key — the check is silently skipped. Password-history enforcement is effectively absent.

Recommendations
  • Raise minimum length from 12 → 14 in the four client validators (SignUpPage, AccountSettingsPage, ResetPasswordPage; plus a shared util if extracted).
  • Re-implement check_password_reuse to actually bcrypt-compare submitted password against each stored hash: 
    CREATE EXTENSION IF NOT EXISTS pgcrypto;
-- store crypt(password, gen_salt('bf', 12)) in password_history.password_hash
-- compare with: crypt(p_password, ph.password_hash) = ph.password_hash
  • Alternatively, delegate reuse policy to Supabase Auth's built-in password-strength settings and remove the custom table.

src/components/StudyContent.tsx:13        dangerouslySetInnerHTML={{ __html: html }}
src/components/EditableCard.tsx:167       dangerouslySetInnerHTML={{ ... }}
src/components/EditableCard.tsx:211       dangerouslySetInnerHTML={{ ... }}

Findings

  • After upgrading to a fixed dompurify (see C-06), keep the sanitizer centralized so future call sites cannot bypass it.

Owner-scoped tables (study_sets, folders, folder_items, password_history) are correctly restricted by auth.uid() = user_id. However, the live-game tables intentionally allow anonymous reads/writes so guest players (who have no auth) can join. The side-effect: any unauthenticated client can modify any participant's score via participants_update USING (true), and can submit answers on behalf of any participant. This is straight-up cheatability.

Recommendations
  • Replace participants_update USING (true) with a policy that checks the caller's player_token via a custom JWT claim or a signed nonce. Example: USING (player_token = current_setting('request.headers', true)::json->>'x-player-token').
  • Same principle for answers_insert: require the submitting client to present the matching player_token.
  • Game scoring / question-progression should move into SECURITY DEFINER RPCs that validate the player's identity and the current question index server-side, rather than letting the client write arbitrary rows.

O-07A07 — Identification and Authentication Failures

Partial
Source
OWASP Top 10 2021
Control ID
A07:2021
Category
Authentication
Control Description
Credential stuffing protection, brute-force defense, no default/weak passwords, secure recovery, session rotation.
Procedure
  1. Read sign-in RPC wiring: check_account_lockout, record_failed_login.
  2. Read the Postgres functions is_account_locked, record_failed_login, can_request_password_reset.
Evidence

Good: lockout at 5 fails/30 min is implemented at the DB level; forgot-password is rate-limited at 5/hour; 12-char minimum password.

Gaps: the client calls check_account_lockout (plural style) but the migration defines is_account_locked — the RPC name mismatch means the client's lockout check silently falls through its try/catch. Separately, the client's forgot-password path calls check_password_reset_rate_limit but the migration defines can_request_password_reset. Both lockout and reset-rate-limit enforcement are therefore currently not enforced end-to-end, despite the SQL functions existing.

Findings

Significant design effort went into rate-limiting, but a naming-convention mismatch between the Postgres layer and the TypeScript caller quietly disables it. Confirm by reading:

// SignInPage.tsx calls:
await supabase.rpc('check_account_lockout', { p_email: email });
// Migration 001 defines:
CREATE OR REPLACE FUNCTION is_account_locked(p_email TEXT) ...

Same issue in ForgotPasswordPage.tsx (check_password_reset_rate_limit vs can_request_password_reset).

Recommendations
  • Rename either side. Easier: create Postgres aliases check_account_lockout and check_password_reset_rate_limit in a new migration that call the existing functions and return { locked: boolean } / { limited: boolean } matching what the client expects.
  • Also call record_failed_login only when the lockout RPC reports "not locked" — currently on every auth failure, so even a locked account keeps recording attempts, which can't lift.
  • Add integration tests that assert both sides agree: e.g., simulate 6 bad logins and assert the 7th returns "locked".
